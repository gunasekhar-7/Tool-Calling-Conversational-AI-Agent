# Path to 9.5 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close every gap the senior review named — one control-flow bug, three trust failures, and the missing evidence — so the project is defensible claim-by-claim instead of impressive-with-asterisks.

**Architecture:** The shape stays FastAPI + LangGraph `StateGraph` + Postgres + Streamlit. Four boundaries move: identity from one shared token to per-customer keys bound at the session, write execution from a commit hidden inside a graph node to exactly one commit at the request boundary, evaluation from scripted-replay-only to replay **plus** a live-model path with confidence intervals and provenance, and operability from logs-only to a metrics endpoint, a bounded shared limiter, measured latency under load, and a runbook.

**Tech stack additions:** `prometheus-client`, `uv.lock`, a `dashboard` optional-dependency extra. No Redis, no Kubernetes, no second datastore.

**Spec:** the senior review in this thread (7.5/10 with 8 findings) plus the six-phase brief. Where they disagree, the review wins.

**Execution status (2026-11-01).** Tasks 1–15 are implemented. The local gate is green: 140
tests, ruff, format, mypy, offline evaluation at 100 % (`n=75`, 95 % CI 95.1–100 %), and
100/100 load requests with 0 errors. Live mode is wired and fails closed in `eval-live.yml`,

## Global Constraints

- No shared master key in production. Every session is bound to an authenticated customer; `POST /v1/sessions` no longer accepts `customer_id`.
- Exactly one `COMMIT` per write request. Repositories call `flush()`, the runtime commits; a failure after the write rolls the whole thing back.
- Quoted numbers come only from committed reports and always carry `n`, the confidence interval, the model id, and the commit hash. Offline path metrics are never presented as model quality.
- Postgres is the only stateful dependency. No new services.
- The dashboard holds no database credentials and no decision authority.
- No metric, badge, or README claim that a command in the verification checklist cannot reproduce.
- Every new or changed endpoint appears in the README's API table in the same task.

## Review Focus

The five failure modes this plan must pin with tests, most likely first:

1. A user message arrives while a write is awaiting approval.
2. Two approvals race, or a decision lands exactly at the TTL boundary.
3. A bearer token is rotated or revoked while a session is live.
4. Adversarial instructions arrive inside tool output or a ticket subject, not just user text.
5. Non-ASCII, emoji, or near-limit input across screening, ticket fields, and grounding.
