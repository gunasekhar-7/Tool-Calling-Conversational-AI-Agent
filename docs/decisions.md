# Decision log

Six decisions that shape the whole system. Each records what it cost and what would
reverse it, because a decision without a reversal condition is just a preference.

---

## ADR-1 — LangGraph instead of raw function calling

**Context.** The agent needs to call tools, loop back to the model, and stop
mid-turn to wait for a human. Raw OpenAI function calling gives a stateless request
and a list of tool calls; everything about "where were we" is the caller's problem.

**Decision.** A LangGraph `StateGraph` with three nodes (`agent`, `tools`, `write`)
and a conditional edge. State is checkpointed per session in Postgres by
`langgraph-checkpoint-postgres`.

**Consequence.** The pause is durable: `interrupt()` persists the paused graph, so
an approval that arrives 40 minutes later — or on another machine after a deploy —
resumes the same state. The cost is a hard dependency on a fast-moving library
(1.x moved several APIs) and a checkpointer that writes to the same database as the
application data.

**What would change it.** If the deployment needed to run without Postgres, or if
upgrades became a recurring breakage, the state machine is small enough (~120 lines
in `agent/agent/graph.py`) to own directly with an explicit `pending_action` table
as the interrupt.

## ADR-2 — Authorization outside the model

**Context.** The plausible failure for a support agent is not a rude sentence; it is
reading or writing another customer's data because the model passed an id it saw
somewhere.

**Decision.** The model never supplies `customer_id`. It comes from the bearer token
at the HTTP boundary (`agent/api/deps.py`), is injected into `ToolContext` by the
server (`AgentRuntime._context`), and every repository query filters on it. A second
gate, `agent/agent/guardrails/policy.py`, validates tool arguments independently of
the prompt.

**Consequence.** A prompt injection that convinces the model to read `ORD-2001`
produces a 404, not a leak — the query cannot return a row that belongs to someone
else. The cost is that the model cannot be asked "what about the other orders?": the
capability simply does not exist, which is the intention.

**What would change it.** An operator console with genuinely cross-customer scope
would need a second principal type with its own token, its own tools and its own
audit trail — not a widened `customer_id`.

## ADR-3 — Grounding against tool receipts, not against the prompt

**Context.** "Don't hallucinate" in a system prompt is a suggestion. A model that
invents an order status is wrong in the one way support cannot tolerate.

**Decision.** Every read tool writes a `tool_receipts` row with the facts it
returned (`agent/tools/receipts.py`). After a turn, `verify()` in
`agent/agent/guardrails/grounding.py` extracts checkable claims (order ids, ticket
ids, statuses, refund windows) from the answer and confirms each one appears in a
receipt from that session. Unsupported claims trigger one repair attempt, then a
template answer built from the receipts.

**Consequence.** The check is conservative and mechanical: it can only validate
claims whose shape it knows (ids, statuses, dates), so a fabricated narrative
sentence can still slip through. It also costs a second model call in the repair
path. In exchange, the failure mode is bounded — a grounding warning and a corrected
answer, not a confident lie.

**What would change it.** A model-based judge could catch softer claims, at the cost
of a second non-deterministic component in the trust path. That trade is not worth
it until the receipt checker is demonstrably the bottleneck.

## ADR-4 — Offline replay *and* live evaluation, reported separately

**Context.** A success rate is the headline number a reader will quote. Two failure
modes are easy and both are dishonest: grading the pipeline with a scripted model
and calling it model quality, or reporting a live number with no interval and no
provenance.

**Decision.** `scripts/evaluate.py` has two modes over the same 25 scenarios. Offline
replays scripted plans (deterministic, runs in CI with no key); live calls the
configured provider. Both emit `pass^1`, `pass^k`, a 95% Wilson interval, per-category
intervals, and provenance (mode, model id, temperature, prompt version, scenario
hash, commit). The report states which interpretation applies.

**Consequence.** CI gates the pipeline (100% required, because a scripted plan is
deterministic); the live number is the one that says anything about the model, and it
is regenerated by a manual workflow. Two numbers to maintain, and the offline one can
never be quoted as quality — a real constraint, enforced by the report's own text.

**What would change it.** If the offline suite stopped catching regressions — no
failure in N runs that live mode later found — the harness would have stopped paying
for itself and the scripted layer would be replaced by recorded traces.

## ADR-5 — Rate limiting in Postgres instead of process memory

**Context.** The first limiter was a `dict` of token buckets. Two API workers meant
two budgets, a restart meant a fresh burst, and memory grew with the number of
sessions ever seen.

**Decision.** One row per customer in `rate_limit_buckets`, consumed with a single
`INSERT … ON CONFLICT DO UPDATE` that refills, caps and takes a token, and returns no
row when it refuses (`agent/agent/guardrails/rate_limit.py`).

**Consequence.** The budget is shared by every worker, survives restarts, and the
table is bounded by the number of customers rather than requests. The cost is one
extra round trip on the hot path, and a limiter that now depends on the database
being up — acceptable, because a turn without the database could not do anything
anyway.

**What would change it.** At a request volume where an extra write per message
dominates, Redis or a token bucket at the edge would be the right move. At this
scale it would add a service to operate for no measured gain.

## ADR-6 — Exactly one commit per write request

**Context.** The write path has several things to persist together: the ticket, the
`pending_actions` state transition, the audit row, and the graph's final checkpoint.
If the ticket commit happened inside a graph node, a later failure would leave a
ticket behind while the caller saw an error.

**Decision.** Repositories `flush()`, they never commit. The approval endpoint owns
the single commit (`AgentRuntime.resolve_approval`): it consumes the row, creates
the ticket and writes the audit row in one transaction, then resumes the graph to
render the reply. The consume step locks the row `FOR UPDATE`, re-validates the
approved preview hash, and relies on unique `stage_key` / `consume_key` constraints
for idempotency. Staging is its own short transaction before the pause.

**Consequence.** "Nothing was saved" is a true statement when the API returns
`write_failed`, and a retried approval replays the first result instead of creating a
second ticket. The transaction closes before the model writes its answer, so no
connection is held across a provider call. The cost is that an approval whose reply
fails returns the committed ticket with a generic reply instead of pretending the
write failed — the correct direction for a decision a human already made.

**What would change it.** Committing inside the graph node would let the model's
reply roll the ticket back, which is worse: a human approved a write and the system
would discard it because a later prose step failed. Only a separate reconciliation
job could justify that shape.

## ADR-7 — An expired approval is settled as a rejection

**Context.** `interrupt()` leaves an assistant tool call in the checkpoint. The TTL
guard only consults `pending_actions`; after expiry it stops refusing messages, but
the checkpoint still holds the unanswered call. A provider rejects a message list
where an assistant tool call has no matching tool result, so the next turn would fail
and every turn after it would fail the same way.

**Decision.** Before the SSE stream starts, `settle_approval_state` examines the
checkpoint. A live proposal still raises `approval_pending`. An expired one is
resumed with `ApprovalResume(silent=True)`: the write node records a rejected tool
result and routes to END. No model reply is generated. An executed action whose
resume was lost is replayed the same way with its ticket id, so the tool call is
answered with the truth.

**Consequence.** Expiry is a clean terminal state and the next message is a valid
provider request. The cost is one graph resume on the first message after an
abandoned approval; it makes no model call and no write. The preflight also returns
the checkpoint's message count, which is what stops the turn from replaying old tool
calls as new activity.

**What would change it.** A checkpointer that can atomically discard an interrupt, or
a write node that does not persist the tool call until approval. Both add more
machinery than one silent resume, and the resume keeps the provider history valid
for every future turn.
